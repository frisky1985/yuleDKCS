> **版本**: 1.0.0 | **日期**: 2026-08-06 | **状态**: ACTIVE

## 1. 目的与流程

本文档用于评估需求变更对**进度 (Schedule)、资源 (Resources)、风险 (Risk)** 的影响，是 SWE.1.BP3 的证据产物。

**触发条件**（满足任一即触发影响分析）:
1. 新增/修改/删除任何 REQ-xxx 需求
2. 上游 RS-xxx 系统需求变更
3. 协议标准（ICCE/CCC/ICCOA）版本升级
4. 架构或接口契约变更（见 `docs/architecture.md` 接口清单）
5. 影响 ASIL 等级的变更

**流程**: 变更申请 → 影响分析（本文档 §3 模板）→ 评审（小马）→ 批准（小明）→ 更新 SRS + 追溯矩阵 → 归档。

## 3. 影响分析记录（首版：ASPICE CL2 证据基线建立）

### 3.1 变更描述

**IA-001**: 建立软件需求基线（REQ-xxx 体系）并补齐 ASPICE CL2 证据链（SRS / 架构 / 集成测试 / 合格性策略 / 追溯矩阵）。该变更**不修改产品功能**，仅新增文档、测试与证据产物。

### 3.2 进度影响 (Schedule)

| 影响项 | 评估 | 说明 |
|:-------|:-----|:-----|
| 交付周期 | 🟢 无影响 | 纯证据补齐，无产品代码改动；集成测试复用已有 e2e/Go 集成套件 |
| 里程碑 | 🟢 无影响 | master 基线不动，新增 commit 独立合入 |
| 回归窗口 | 🟡 少量增加 | 新增 tests/integration pytest 套件纳入 `yuleosh ci run 2`（≤60s 超时上限） |
| 维护成本 | 🟡 持续 | 需求/追溯矩阵需随变更维护（每次 REQ 变更重跑 `yuleosh traceability matrix`） |

### 3.3 资源影响 (Resources)

| 资源 | 需求 | 现状 | 缺口 |
|:-----|:-----|:-----|:-----|
| 人力 | 文档/证据编制 1 人 | 小克（本 Sprint） | 无 |
| 工具链 | yuleosh CLI | 已安装 (v3.4.0) | 无 |
| CI | pytest + Go toolchain | 已有三层 CI | 集成测试纳入 L2 后需保持 ≤60s |
| 硬件 | HIL 测试台 | S32K312 EVB 已有报告归档 | 真机持续回归未建（见风险 R-04） |

### 3.4 风险影响 (Risks)

| 风险 ID | 描述 | 等级 | 缓解措施 |
|:--------|:-----|:----:|:---------|
| R-01 | 追溯矩阵依赖 yuleosh 工具链解析，检查器存在 "unknown check type" 识别限制（如 REQ-xxx 唯一性、stubs/drivers、证据归档等检查项） | 🟡 中 | 记录为工具链限制（非仓库缺陷）；人工核对 SRS 结构满足唯一标识 + SHALL 要求 |
| R-02 | 集成测试（pytest）与 Go 集成套件并行维护，可能漂移 | 🟡 中 | `tests/integration/README.md` 明确定位：pytest = 契约/数据流验证，Go 套件 = 组件级 E2E；CI 双跑 |
| R-03 | SRS 需求状态与实际实现不一致（Approved vs Implemented） | 🟡 中 | 状态字段随实现推进更新；P0-5 追溯矩阵自动暴露无测试覆盖需求 |
| R-04 | SIL/HIL 结果仅归档静态报告，无硬件持续回归 | 🟡 中 | 合格性策略定义 HIL 回归频率（每个固件版本发布前） |
| R-05 | 需求数量增长导致追溯矩阵膨胀 | 🟢 低 | 按功能域分组维护；变更走本流程 |

### 3.5 影响范围确认

| 受影响产物 | 是否影响 | 动作 |
|:-----------|:--------:|:-----|
| 产品代码（Go/C/Java） | ❌ | 无 |
| 对外接口契约 | ❌ | 无（接口清单仅盘点，不修改） |
| CI 流水线 | ⚠️ 部分 | `tests/integration/` 纳入 `yuleosh ci run 2`；三层门禁不变 |
| 文档/证据 | ✅ | SRS/架构/合格性策略/追溯矩阵新增或更新 |

**结论**: IA-001 变更风险可控（低风险、零产品代码影响），批准执行。
