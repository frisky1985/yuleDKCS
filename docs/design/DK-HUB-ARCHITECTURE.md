# Digital Key Hub 架构设计方案

**日期**: 2026-06-01 | **更新**: 2026-06-01 | **基于**: CCC 3.0 / ICCOA DK3.0-4.0 / ICCE 协议分析

---

## 一、核心设计思路

> **DK Hub 不做钥匙。DK Hub 只做授权决策。**
>
> 钥匙生成在车厂 PKI，Hub 只是通知 DK Server

## 二、为什么需要这个拆分？

### 现状问题

```
当前 yuleDKCS 架构:
App → yuleDKCS Hub → DKCS (管理密钥+存储密钥) → Adapter → TSP → 车端
                       └── 密钥材料在 DKCS 手里 ──┘
```

三个协议读下来的核心发现：

| 协议 | 密钥材料的归属 | 对云端的要求 |
|:----|:-------------|:------------|
| **CCC** | 车端 SE050 存储，云端不下发私钥 | 云端只做证书链管理和配对编排 |
| **ICCOA** | 车端 BLE 通道协商，云端不参与密钥交换 | 云端只需同步权限和状态 |
| **ICCE** | 车端 SE + 边缘计算，国密密钥在本地 | 云端只需做绑定管理 |

**三个协议都不要求云端持有密钥材料。** 密钥材料天然就应该在车端 SE050 和手机 SE/Keychain 里。

### 矛盾

当前 yuleDKCS 的 DKCS 服务试图同时做两件事：

```
DKCS = 密钥编排（谁有什么权限） + 密钥存储（密钥材料）  ← 混淆了职责
```

主机厂说："我的 KMS (AWS KMS / Azure Key Vault / HSM) 不能被你碰。" 这是真实的部署障碍。

## 三、Digital Key Hub 架构

### ⚠️ 关键边界：Token 签发机，不碰钥匙

> **DK Hub = Token 签发机，不碰钥匙。**
>
> **Token** = 授权凭据（由 Hub 签发，向车厂证明

### 3.2 职责边界

```
Digital Key Hub 做:
┌── ✓ 用户注册/登录/多设备管理
├── ✓ 钥匙生命周期编排（创建/分享/吊销/挂起/恢复）
├── ✓ 权限位解析 + 有效期 + 使用次数
├── ✓ 协议转换（CCC ⇄ ICCOA ⇄ ICCE 统一内部协议）
├── ✓ 手机厂商适配器路由（CCC→Apple/Samsung, ICCOA→小米/OPPO）
├── ✓ 多设备配钥（新手机登录→按能力配钥匙）
├── ✓ 审计日志（谁、何时、对哪辆车、做了什么）
└── ✓ 车辆状态转发（车端→云端→手机端）

Digital Key Hub 不做:
┌── ✗ 不生成钥匙（只做授权决策，不触发密钥生成）
├── ✗ 不存储私钥/证书（钥匙材料全程在车厂 PKI/TSP）
├── ✗ 不直接对接车端（车端通信由 DK Server 负责）
├── ✗ 不签发证书（由车厂 PKI 签发）
├── ✗ 不处理车端固件 OTA
└── ✗ 不集成手机钱包 SDK
```

## 四、对现有代码的影响

### 不变的部分

| 模块 | 说明 |
|:----|:-----|
| `embedded/` | 三协议栈不变——车端代码无需改动 |
| `frontend/` | Android/iOS SDK 不变——SDK只跟Hub通信 |
| `backend/cloud/hub/` | **HUB 重命名 + 职责聚焦** |
| `backend/adapters/` | Java TSP 适配器不变——它们是车厂接口 |

### 需要调整的部分

| 模块 | 调整 |
|:----|:-----|
| `backend/dkcs/` | **剥离密钥存储职责**，只保留密钥编排逻辑 |
| `KeyStore` 接口 | 改为 **OEM KMS 适配器接口**，由车厂实现 |
| `KeyManagementService` | 抽掉 key material 相关代码，专注编排 |
| 数据库 | 只存 key metadata（谁/什么权限/有效期），不存私钥 |

## 五、部署模式

### 三层架构总览

```
手机App/钱包
     │
     ▼
DK Hub  (我们部署 / SaaS)
  ├── 手机厂商适配 (Apple CCC, Samsung CCC, 小米 ICCOA...)
  ├── 用户管理 (账号/多设备/认证)
  ├── 钥匙编排 (创建/分享/吊销/挂起)
  └── 统一协议转换
     │ gRPC 双向 TLS
     ▼
OEM DK Server  (车厂自建 / 云端)
  ├── 密钥材料管理 (SE050写入/证书签发)
  ├── KMS 集成 (AWS KMS / Azure KV / HSM)
  └── 车端通信 (MQTT→TCU)
     │
     ▼
OEM TSP  (车厂已有 / 内网)
  ├── 车辆注册
  ├── 数据上报
  └── 远程诊断
```

### 三种部署模型

```
模式A: Hub SaaS（轻量）
  DK Hub         = 我们部署在云端
  OEM DK Server  = 我们提供参考实现, 部署在车厂云
  OEM TSP        = 车厂原有, 不变
  适用: 中小车厂 / 快速接入
  优点: 开箱即用

模式B: Hub On-Prem（合规）
  DK Hub         = 作为容器部署在车厂内网
  OEM DK Server  = 车厂自建
  OEM TSP        = 车厂原有
  适用: 大型车厂, 数据不出境需求
  优点: 密钥材料完全在车厂控制下

模式C: Hub 混合（最推荐）
  DK Hub         = 我们 SaaS, 负责手机厂商侧和编排
  OEM DK Server  = 车厂自建, 部署在车厂云
  OEM TSP        = 车厂原有
  中间通过 gRPC 双向 TLS 通信
  适用: 主流车企
  优点: 手机厂商统一接入 + 密钥材料不出厂
```

## 六、一句话总结

**把 DKCS 拆成两层：**
- **Digital Key Hub** = 钥匙编排层（轻量，无密钥材料）
- **OEM KMS Adapter** = 密钥材料层（车厂自管）

这样主机厂放心（密钥不出去），手机厂商开心（统一接入），Hub 轻了（不用管合规审计）。
