# ICCOA/T 002-2024 — 数字车钥匙3.0 规范知识库

> 来源: ICCOA DK 4.0_251201.pdf (217 pages)
> 规范编号: ICCOA/T 002-2024
> 名称: 数字车钥匙3.0 (Digital Car Key 3.0)
> 状态: 已发布，中文

## 1. 范围

本文件规定了数字车钥匙的系统架构和功能要求、证书、流程、BLE接口、NFC接口、UWB接口、APDU命令接口、数字钥匙框架接口、服务器接口、远程控车、场景等。
适用于 NFC、蓝牙和 UWB 数字车钥匙。

## 2. 系统架构

### 2.1 架构概览（§5.1, p.9-10）

数字车钥匙系统包含四部分：
- **车服务器** (Car Server) — 车企端，管理钥匙生命周期、签发证书、与车通信
- **设备服务器** (Device Server) — 手机厂商端，管理设备端钥匙、与车服务器同步
- **车** (Vehicle) — 具备 BLE/NFC/UWB 能力，连接互联网
- **设备** (Device) — 手机/可穿戴，具备 DKF (数字钥匙框架)、TEE/SE

**ICCOA 没有 Relay Server 概念。** 分享通过车服务器与设备服务器之间的 S2S API 完成。

### 2.2 车服务器（§5.2.1, p.11）

功能要求：
a) 管理车服务器证书，签发车服务器证书，生成中间分享证书 CSR
b) 保存、下发蓝牙配对信息
c) 建立与车之间的数据通道
d) 钥匙生命周期管理
e) 与设备服务器同步

### 2.3 设备服务器（§5.2.2, p.11）

功能要求：
a) 钥匙生命周期管理
b) 与车服务器同步

## 3. 钥匙类型（§3, p.7-8）

| 钥匙类型 | 说明 |
|:--------|:-----|
| **车主钥匙** (Owner DK) | 一辆车生成的第一把钥匙，每辆车唯一，可分享 |
| **好友钥匙** (Friend DK) | 被车主钥匙分享出来的钥匙，不可继续分享 |
| **中间分享证书** | CA 模式下用于签发好友钥匙的中间证书 |

## 4. 钥匙状态（§3.12, p.9）

| 状态 | 说明 |
|:----|:-----|
| 未激活 | 已下发但未使用（含未下发） |
| 已激活 | 已完成首次交易 |
| 已冻结 | 暂停使用 |
| 已删除 | 已被撤销 |

## 5. 钥匙信箱（§7.4.7, p.46-47）

> **ICCOA 的"钥匙信箱"是设备端 DKF 功能，不是服务器端的中继/转发。**

- DKF 可具备钥匙信箱功能，供车、车 APP 读写信息
- 钥匙信箱数据保存在 DKF 中，DKF 数据被清除时信箱数据丢失
- 钥匙信箱与钥匙绑定，每个钥匙只有一个信箱
- 车 APP 与车写入的是同一个信箱

读写通过 BLE 协议（§8.3.12, p.108）或 DKF API（§12.3.27-28, p.136-137）完成。

### DKF API 定义（§12.3.27-28）

**读取钥匙信箱（§12.3.27）:**
- 读取指定钥匙的信箱内容
- 输入: Key ID
- 输出: mailbox 内容（bytes）

**写入钥匙信箱（§12.3.28）:**
- 向指定钥匙的信箱写入内容
- 输入: Key ID, 写入内容（bytes）
- 输出: 成功/失败

## 6. 分享钥匙流程

### 6.1 分享架构

ICCOA 的钥匙分享有两种账号体系，**都不需要 Relay Server**：

```
车账号体系分享         手机账号体系分享
─────────────────      ─────────────────
车 App 发起              Native App 发起
通过车服务器传递          通过设备服务器传递
好友通过车 App 接收      好友通过 Native App 接收
```

### 6.2 CA 模式 vs 非CA 模式

| 模式 | 证书体系 | 流程差异 |
|:----|:---------|:---------|
| **CA 模式** | 车服务器 CA 签发车主钥匙 → 中间分享证书 → 好友钥匙 | 使用中间分享证书 (getMidCsr/putMidCert) |
| **非CA 模式** | 车主钥匙签发分享证明 | 使用 Sharing Attestation Request (getSar/putSharingAttestation) |

### 6.3 通过车账号体系分享（§7.6.1, p.51-54）

16 步流程，核心 S2S 调用：
1. 车 App → 车服务器: 分享请求（有效期、权限、好友账号）
2. 车服务器 → 车 App: ownerSessionId
3. 车主 DKF → 设备服务器 → 车服务器: 请求中间分享证书 (getMidCsr)
4. 车服务器 → 设备服务器 → 车主 DKF: 中间分享证书 CSR
5. 车主 DKF → 设备服务器 → 车服务器: 签发的中间分享证书 (putMidCert)
6. 车服务器 → 好友车 App: friendSessionId（分享凭证）
7-10. 好友设备创建密钥对 → 请求签发好友证书 (share/sign) → 获取证书链
11. 好友 DKF → 设备服务器 → 车服务器: 注册钥匙 (trackKey)
12-13. 车服务器 → 车: 证书链下发（在线/离线）
14-16. 激活 → 通知 → 状态同步 (notifyKeyEvent)

### 6.4 通过手机账号体系分享（§7.6.2, p.54-57）

24 步流程，核心差异：从 Native App 发起，设备服务器做编排。
- 使用 share/genSession 生成 sessionId
- 其他与车账号体系相同

## 7. 服务器接口 — Server to Server API（§13, p.140-155）

### 7.1 通信要求（§13.2）

- 双向 SSL 安全通信
- REST 风格 HTTP，JSON 格式
- 通用请求头: X-ICCOA-Request-ID, X-ICCOA-Timestamp, X-ICCOA-Device-OEM-ID/X-ICCOA-Vehicle-OEM-ID

### 7.2 车服务器 API 接口（§13.5）

| 接口 | 路径 | 说明 |
|:----|:-----|:-----|
| 签发车主钥匙 | op/sign | 签发车主数字钥匙证书 |
| 请求中间分享证书(CA) | share/getMidCsr | 车服务器生成中间分享证书 CSR |
| 签发中间分享证书(CA) | share/putMidCert | 接收已签发的中间分享证书 |
| 签发好友钥匙 | share/sign | 签发好友数字钥匙证书 |
| 撤销分享 | share/cancel | 释放 shareId 等资源 |
| 生成分享sessionId | share/genSession | 生成 ownerSessionId/friendSessionId |
| 注册钥匙 | trackKey | 注册数字钥匙到车服务器 |
| 管理钥匙 | manageKey | 钥匙状态管理（冻结/恢复/删除） |
| 钥匙事件通知 | notifyKeyEvent | 设备服务器通知车服务器钥匙事件 |
| 获取钥匙配置信息 | getVehicleProfile | 车辆钥匙配置和权限信息 |
| 健康检查 | healthCheck | 服务器健康状态检查 |
| 获取分享证明请求(非CA) | share/getSar | 生成 Sharing Attestation Request |
| 签发分享证明(非CA) | share/putSharingAttestation | 接收签发的分享证明 |
| 车企自定义数据批量推送 | notifySyncKeyPropBatch | 车企自定义数据批量推送通知 |

### 7.3 设备服务器 API 接口（§13.6）

| 接口 | 说明 |
|:----|:-----|
| manageKey | 钥匙状态管理 |
| syncKeyInfo | 钥匙信息同步（车服务器 → 设备服务器） |
| healthCheck | 健康检查 |
| syncKeyPropDataBatch | 车企自定义数据批量同步 |

### 7.4 详细错误码（§13.4, p.145）

| 错误码 | 说明 |
|:------|:-----|
| 40000 | 无效参数 |
| 40001 | 参数校验失败 |
| 40002 | 缺少必填参数 |
| 40003 | 参数格式错误 |
| 40004 | 参数值不在有效范围 |
| 40005 | 请求过于频繁 |
| 40100 | 未授权 |
| 40101 | 签名验证失败 |
| 40102 | 证书验证失败 |
| 40103 | 证书已过期 |
| 40300 | 无权限 |
| 40400 | 资源不存在 |
| 50000 | 服务器内部错误 |
| 50001 | 服务暂时不可用 |

## 8. 撤回钥匙（§7.8, p.70-81）

5 种撤销方式：
- 通过 Native App 撤销
- 通过车端撤销
- 通过设备服务器撤销
- 通过车服务器撤销
- 通过车 App 本地撤销

## 9. 冻结与恢复钥匙（§7.9, p.82-83）

- 通过设备服务器冻结/恢复 (manageKey)
- 通过车服务器冻结/恢复 (manageKey)

## 10. BLE 钥匙信箱（§8.3.12, p.108）

BLE 协议中定义了读写钥匙信箱的 APDU 格式：
- 读取钥匙信箱: 从 DKF 读取信箱内容
- 写入钥匙信箱: 向 DKF 写入信箱内容

## 11. ICCE 对比

ICCE (华为主导) 与 ICCOA 架构类似：
- 以车厂 OEM 为中心做分享
- 车服务器 + 设备服务器 S2S API
- 没有 Relay Server
- 差异主要在证书格式、加密算法、流程细节

## 12. 当前差距分析

### 版本号问题

| 项 | 规范 | 当前代码 | 结论 |
|:---|:-----|:---------|:-----|
| 协议版本号 | ICCOA/T 002-2024 (数字车钥匙3.0) | `iccoa_dk40` | ⚠️ 命名不匹配。规范是 DK 3.0，但协议名叫 dk40（疑似预命名） |

### Adapter 实现差距

当前 `ICCOAAdapter` 实现了 `Adapter` 接口的全部方法，但**所有方法都是 stub** — 未对接任何厂商的真实 REST API。

| 方法 | 当前实现 | ICCOA 规范要求 | 差距 |
|:-----|:---------|:-------------|:----:|
| `BindKey` | 返回空 key | §5.2 设备服务器/车服务器 | 需调用厂商钱包 API |
| `UnbindKey` | 返回 nil | §7.8 撤销钥匙 | 需调用对应厂商接口 |
| `RevokeNotify` | 返回 nil | §7.8 | 需推送通知 |
| `ShareKey` | 返回随机 shareId/shareCode | §7.6.1/7.6.2 分享流程 | **严重差距** — 需实现车服务器 ↔ 设备服务器 S2S API |
| `AcceptShare` | 返回 stub key | §7.6 接受分享 | 需完成证书链获取 |
| `Notify` | 返回 nil | §13.5.9 notifyKeyEvent | **需实现** |
| `HealthCheck` | 返回 ok | §13.5.11 / §13.6.3 | ✅ stub 够用 |

### 需要实现的 S2S API 优先级

为了达到量产级，需要依次实现：

| 优先级 | API | 说明 |
|:------:|:----|:-----|
| P0 | **share/genSession** | 分享流程的基础 — 生成 ownerSessionId/friendSessionId |
| P0 | **trackKey** | 好友钥匙注册 |
| P0 | **notifyKeyEvent** | 钥匙状态回传（激活/冻结/删除） |
| P1 | share/getMidCsr | CA 模式下中间分享证书 CSR |
| P1 | share/sign | 签发好友钥匙 |
| P1 | share/cancel | 撤销分享 |
| P1 | manageKey | 钥匙状态管理 |
| P2 | op/sign | 签发车主钥匙 |
| P2 | getVehicleProfile | 车辆配置信息 |
| P2 | share/getSar | 非CA 模式分享证明 |

### 建议

1. **协议名修正**: 确认规范版本号。当前文件名为 "ICCOA DK 4.0" 但规范内容写的是 "数字车钥匙3.0"。建议确认后统一协议名
2. **优先对接车服务器 API**: ICCOA 的核心是车服务器，Adapter 应优先实现车服务器侧的 S2S API
3. **与 CCC 的 Relay Server 隔离**: ICCOA 不需要 Relay Server，不要让 share 流程走 Mailbox
